# Launcher context and application content

Use `Dolphin.IO.LaunchContent.Mount()` to find files beside a launched GameCube
executable. It reads the captured launcher path, translates supported device
aliases, mounts or borrows the corresponding filesystem, and returns an explicit
content root. It does not change the process working directory. Applications
that need package identity checks or a fallback for loaders without usable
arguments supply those policies through `LaunchContentOptions`.

## Reading a file beside the executable

For a launch path such as `cardb:/apps/example/default.dol`, the default content
root is `cardb:/apps/example/`:

```csharp
using System;
using Dolphin.IO;

var result = LaunchContent.Mount();
if (!result.Succeeded)
{
    Console.WriteLine("Content mount failed: " + result.Failure);
    return 1;
}

using var content = result.Content!;
using var input = content.OpenRead("assets/config.bin");
var firstBlock = new byte[256];
int bytesRead = input.Read(firstBlock, 0, firstBlock.Length);
Console.WriteLine(content.RootPath);
Console.WriteLine(bytesRead);
return 0;
```

The `using` declarations dispose the stream before the content mount. Keep the
content object alive for as long as its files are needed. An explicit launch-path
overload is also available:

```csharp
var result = LaunchContent.Mount("sdb:/apps/example/default.dol", options);
```

This overload uses the supplied hint instead of captured `argv[0]`; it performs
the same validation and mounting. For an authoritative executable or
containing-directory hint, the source file and its containing directory must
exist before the candidate is accepted.
A path alone does not establish that the files belong to the correct game build.

### Result and content access

`LaunchContentResult` provides `Succeeded`, nullable `Content`, `Failure` and an
`Attempts` array for diagnostics. Each attempted candidate is bounded; the
resolver does not recursively scan a device or select the last mounted volume.
Each `LaunchContentAttempt` records `SourcePath`, `RootPath`, `Device`, `Failure`
and the underlying `MountFailure` when mounting fails.

A successful `LaunchContent` exposes:

| Member | Meaning |
| --- | --- |
| `FileSystem` | `MountedFileSystem` access bound to the selected mount generation. |
| `Device` | The resolved SDK `StorageDevice`. |
| `RootPath` | Canonical content directory with a trailing slash. |
| `SourcePath` | Canonical source path; empty for a directory fallback without a source file. |
| `LaunchPath` | Original launcher hint, before alias translation. |
| `IsFallback` | Whether an explicitly configured fallback supplied the content. |
| `IsValid` | Whether the content object still has its selected mount generation. |
| `OpenRead(child)` | Opens a relative file through the generation-checked filesystem. |
| `GetPath(child)` | Produces a canonical path for an API that accepts a filename. |
| `Dispose()` | Releases only mounts acquired by the resolver that still have the recorded generation. |

Child paths stay under the content directory: absolute paths, device prefixes
and dot components (`.` or `..`) are rejected. `RootPath` and `GetPath()` results are
ordinary strings. Later path-based I/O addresses the current occupant of that
namespace; it is not bound to the original mount lifetime. Use `OpenRead()` when
that distinction matters. See [mount generations](storage-runtime.md#discovering-and-restoring-mounts).
The helper checks the backend limits before I/O: at most 1023 UTF-8 bytes for a
full path, 255 UTF-8 bytes per component and 64 components. The content directory
and child path must fit those limits together.

## Validate a build and configure bounded fallbacks

The SDK cannot decide which package is the application's intended content.
`Validate` receives a mounted candidate and returns `true` to accept it or
`false` to reject it. For example, an AnimalTown-style standalone installation
can keep the existing exact `content.id` check and required-file checks:

```csharp
using System;
using System.IO;
using Dolphin.IO;
using Dolphin.Storage;

static bool MatchesThisBuild(LaunchContent candidate)
{
    // Generated by the application build; compare the complete ASCII identity,
    // including its version, source digest, runtime profile and line endings.
    string expected = BuildInfo.ContentIdentity;
    if (expected.Length == 0 || expected.Length > 512) return false;

    try
    {
        using (var identity = candidate.OpenRead("content.id"))
        {
            if (identity.Length != expected.Length) return false;
            var bytes = new byte[expected.Length];
            int offset = 0;
            while (offset < bytes.Length)
            {
                int count = identity.Read(bytes, offset, bytes.Length - offset);
                if (count <= 0) return false;
                offset += count;
            }
            for (int i = 0; i < bytes.Length; i++)
                if (bytes[i] != expected[i]) return false;
        }

        string[] required = {
            "default.dol", "runtime.cfg", "buildings.bin", "wordmark.dndtex",
            "savebanner.rgb5a3", "saveicon.rgb5a3"
        };
        foreach (string name in required)
        {
            using var file = candidate.OpenRead(name);
        }
        return true;
    }
    catch (FileNotFoundException) { return false; }
    catch (DirectoryNotFoundException) { return false; }
}

var options = new LaunchContentOptions
{
    Validate = MatchesThisBuild,
    Fallbacks = new[] {
        new LaunchContentLocation(
            MountConfiguration.BlockVolume(StorageDevice.SdSerialPort2),
            "apps/animaltown"),
        new LaunchContentLocation(
            MountConfiguration.BlockVolume(StorageDevice.SdSlotB),
            "apps/animaltown"),
        new LaunchContentLocation(
            MountConfiguration.BlockVolume(StorageDevice.GcLoader),
            "apps/animaltown")
    }
};
var result = LaunchContent.Mount(options);
```

`BuildInfo` and the listed files belong to the example application, not the SDK.
This validator checks a small exact identity file without loading the asset set
into RAM. It treats missing files as rejection and lets other errors propagate.
Close all streams inside the validator. Do not dispose the candidate or change
mounts from the callback. A validator exception triggers cleanup and propagates;
it is not treated as permission to choose another installation.

Fallbacks are empty by default. At most 16 `LaunchContentLocation` entries may
be supplied, and every entry's syntax is checked before the first mount. Each
location takes a `MountConfiguration` and an optional relative directory; the
default directory is the volume root. Existing configuration factories retain
their partition, filesystem and cache options. Locations are attempted in the
supplied order. When a validator is supplied, it must accept a candidate before
selection.

Fallbacks handle missing, well-formed relative or unsupported launcher metadata. A malformed
absolute path fails with `InvalidPath` without probing. Once a supported absolute
source path is authoritative, its mount, file or validation failure does not
silently select a different fallback installation. Resolve an incorrect launch
path or package instead of weakening an identity check.

## Swiss aliases and ambiguous DVD paths

The resolver recognizes the following launch-path spellings:

| Launch prefix | SDK device and canonical prefix |
| --- | --- |
| `carda:/`, `sda:/` | `SdSlotA`, `carda:/` |
| `cardb:/`, `sdb:/` | `SdSlotB`, `cardb:/` |
| `sd:/`, `sdc:/`, `sd2:/`, `sd2sp2:/` | `SdSerialPort2`, `sd:/` |
| `gcloader:/`, `gcldr:/` | `GcLoader`, `gcloader:/` |
| `dvd:/` | Logical disc or Swiss's GC Loader alias; see below. |

Swiss translates its private names before passing arguments: for example,
`sdc:/` becomes `sd:/` and `gcldr:/` becomes `dvd:/`. This is a launcher
convention, not proof of hardware identity. Some other loaders use generic names
differently; they need an explicit canonical path or configured fallback.

`DvdSource` defaults to `LaunchContentDvdSource.Automatic`. Automatic `dvd:/`
resolution requires a validator and otherwise returns `AmbiguousSource`.
It considers an established volume first; otherwise it tries the logical disc
and then raw GC Loader, cleaning up a rejected acquired candidate before moving
on. An application that already knows the interpretation can specify
`LaunchContentDvdSource.Disc` or `LaunchContentDvdSource.GcLoader`.

Existing conflicting mount configurations are not replaced. In particular, raw
GC Loader startup can reset the drive. The resolver does not probe it while an
active physical DVD mount would be disturbed; that case reports `MountFailed`
with the underlying `ConfigurationConflict`. Firmware and driver support still
determine whether an identified device can actually mount.

The source of these conventions is the official
[libogc2 Swiss interaction guide](https://github.com/extremscorner/libogc2/wiki/Interactions-with-Swiss)
and Swiss's
[alias translation](https://github.com/emukidid/swiss-gc/blob/92e63a8f71fc73c3ace17d020ce2790265129958/cube/swiss/source/util.c#L92-L127).

## Companion ISO/GCM arguments

`argv[0]` need not name a DOL. Swiss may provide a companion `data.iso`, a
same-basename `.iso`, or the disc image containing the executable. The SDK keeps
this as launch metadata rather than assuming every hint ends in `.dol`.

`ImageMode` defaults to `LaunchContentImageMode.ContainingDirectory`. An image
hint therefore selects its containing directory, just like an executable hint.
This mode is appropriate when resources live beside the DOL and its companion
image.

To read the files inside a plain GameCube ISO/GCM instead:

```csharp
var result = LaunchContent.Mount(new LaunchContentOptions {
    ImageMode = LaunchContentImageMode.MountImage,
    Validate = ValidateDiscContent
});
```

The source block volume is mounted or borrowed, and the image is presented as
read-only FST content at `dvd:/`. `SourcePath` identifies the canonical image
source while `RootPath` identifies the content inside it. The validator in this
example must check files inside the image; a folder-specific check for
`default.dol` would usually be inappropriate there.

With a logical-disc interpretation of `dvd:/`, the content can instead be the
physical or ODE-selected disc's FST. Its launcher-supplied image filename may
exist outside that FST and is not required as a file inside the mounted disc.
Use the validator to establish the identity of the content actually exposed.
Here `SourcePath` remains the canonical launcher hint, not proof of which image
the drive exposes. If an existing SDK image mount is reused, its actual image
path is `FileSystem.Info.LastSuccessfulConfiguration.ImagePath`.

Mounting supports plain GameCube ISO/GCM files, not NKit, RVZ, CISO or Wii images.
The resolver does not extract images or call `Storage.SelectGcLoaderDiscImage`;
it does not change the drive's physical image mapping. Only one SDK `dvd:/`
filesystem can be mounted at once. A conflicting active disc/image is reported,
not replaced. See [image-backed storage](storage-runtime.md#gc-loader-and-unified-gamecube-dvd-filesystems).

## Mount ownership and execution context

Resolve content on the application executor before starting workers that use
storage. Serialize mounting, unmounting and content disposal with other mount
lifecycle operations, and keep the validator free of mount changes. Ownership
is tracked using mount snapshots and generations; this is not an atomic
cross-thread mount lease.

The resolver borrows a compatible existing mount and owns only mounts it
acquires. Rejection releases its acquired mounts. Disposal releases the content
image before an acquired source volume and leaves borrowed mounts intact.
Cleanup skips mounts whose generation has changed.
Close every stream before disposing content; unmount refuses open handles.
Cleanup failure stops resolution rather than proceeding with a leaked candidate.

Neither this resolver nor `LaunchContext` makes the host folder containing a DOL
visible inside Dolphin. Directly opening a PC `default.dol` does not attach its
sibling assets as a GameCube volume. Resources still need a supported physical
or emulated storage device, a disc image, or an explicitly configured compatible
backend. Setting a PC working directory is not a substitute for that volume.

## Raw incoming context

Applications can still read `Dolphin.IO.LaunchContext.ExecutablePath`,
`ArgumentCount`, `GetArgument(index)` and `GetArguments()` without mounting
anything. This is independent of the managed Main signature. `GetArguments()`
returns a new array. Despite its name, `ExecutablePath` is the launcher's raw
`argv[0]` claim and can contain an image path.

The SDK snapshots libogc CRT argc/argv before platform or managed initialization.
It retains at most 64 arguments and 4096 UTF-8 bytes, validates cached MEM1 ranges
on GameCube and rejects incomplete or oversized input atomically. Missing or
invalid input produces zero arguments and an empty executable path. The source
buffer can be reused after startup. Applications that use neither incoming
context nor captured-path resolution do not enable capture or retain its
approximately 4 KiB buffer. Wii and Wii U are unsupported.

The raw context does not infer a working directory, mount devices or certify a
path. `LaunchContent` is the opt-in layer that resolves that hint using the
explicit policies above.

## Validation scope

Native and real AOT host fixtures exercise argument capture and resolver logic,
including missing arguments, UTF-8, source-buffer reuse, bounds, MEM1 address
limits, the 64/4096 ceilings, fallback and mount-lifetime behavior. Host or fake
backend success is not a claim that a physical adapter, firmware version or
launcher handoff has been qualified. Actual Swiss-to-application handoff,
SD2SP2/SD Gecko/GC Loader media and firmware interactions still require target
testing.
